# Сравнительный анализ подходов к интеграции корпоративных данных в большие языковые модели

**Формат исследования:** Дипломная работа (ВКР) и программный комплекс  
**Сравниваемые подходы:** Легковесный RAG (продукт **Harness RAG** на базе векторной библиотеки **FAISS**) vs Fine-Tuning (**SFT** локальной модели, развернутой через **Ollama**)  
**Ключевой фокус:** Сквозная система технических, инженерных и качественных метрик (**Latency**, **JCR**, **время разработки**, **сложность подготовки данных**) с переходом в детальное **технико-экономическое обоснование (CAPEX, OPEX, TCO, CPUQ, ROI, срок окупаемости)**.

---

## 1. Концепция и рамки исследования

В работе проводится строгое сравнение двух фундаментально противоположных подходов к интеграции закрытых корпоративных данных в локальные большие языковые модели (On-Premise контур без использования внешних облачных API и без смешения в гибридные схемы):

1. **Подход А — Экстернализация знаний (Продукт «Harness RAG» на базе FAISS)**:
   * Локальная языковая модель (развернутая в **Ollama**) используется без изменения весов.
   * Корпоративные документы индексируются в легковесной векторной библиотеке **FAISS** (`IndexFlatIP`, `IndexIVFFlat`, `IndexHNSWFlat`).
   * Поверх векторного поиска работает модуль **Constraint Harness** — программный контур формирования строгого промпт-контракта и алгоритмической пост-валидации ответа на соблюдение корпоративных ограничений.
2. **Подход Б — Интернализация знаний (SFT локальной модели в Ollama)**:
   * Корпоративные документы трансформируются в инструктивный датасет формата `ChatML`.
   * Локальная модель дообучается методом **Supervised Fine-Tuning (LoRA / QLoRA)**, адаптеры объединяются с базовыми весами, квантизуются в формат **GGUF** и разворачиваются на локальном инференс-сервере **Ollama** для прямых ответов без внешнего поиска.

## 3. Подробный план дипломной работы (По главам и параграфам)

### Введение
* **Актуальность темы:** потребность предприятий во внедрении локальных LLM на внутренних закрытых данных при жестких требованиях информационной безопасности, ограниченном бюджете и регулярном обновлении корпоративных регламентов.
* **Научно-практическая проблема:** отсутствие единой количественной методики, связывающей технические метрики работы модели (задержка ответа Latency, совместный показатель удовлетворенности и соблюдения ограничений JCR) с инженерными затратами на подготовку данных и совокупной стоимостью владения (TCO).
* **Объект исследования:** процессы интеграции корпоративных данных в локально развернутые большие языковые модели.
* **Предмет исследования:** сравнительная техническая и экономическая эффективность легковесной архитектуры **Harness RAG (на базе FAISS)** и дообучения **SFT (на базе Ollama)**.
* **Цель и задачи исследования, научная новизна, практическая значимость.**

---

### Глава 1. Теоретические и методологические основы интеграции корпоративных данных в большие языковые модели

* **1.1. Специфика корпоративных данных и требования бизнеса к локальным LLM-системам**
  * Требования локального контура (On-Premise), высокая частота изменений внутренних нормативов (проблема устаревания знаний — *Knowledge Drift*), необходимость строгого соблюдения формальных ограничений.
* **1.2. Архитектура легковесного RAG и математические основы векторной библиотеки FAISS**
  * Принцип экстернализации знаний. Преимущества встраиваемой библиотеки **FAISS** перед тяжелыми клиент-серверными векторными СУБД для сегмента малого и среднего корпоративного внедрения.
  * Математические модели индексов FAISS: точный поиск по скалярному произведению (`IndexFlatIP`), инвертированные списки (`IndexIVFFlat`) и иерархические графы (`IndexHNSWFlat`).
* **1.3. Адаптация моделей методом Supervised Fine-Tuning (SFT) и локальный сервисинг через Ollama**
  * Принцип интернализации знаний в параметры модели. Параметрически-эффективное дообучение (`LoRA`, `QLoRA`), математическая модель низкоранговой декомпозиции весов.
  * Квантизация моделей в формат `GGUF` (`llama.cpp`) и архитектура локального сервера **Ollama**. Фундаментальные ограничения SFT: галлюцинации на точных численных данных и инерция весов при изменении исходных документов.
* **1.4. Система метрик комплексной оценки: от технических показателей к экономическим**
  * Критический обзор стандартных метрик оценки LLM.
  * Формализация композитной метрики **JCR (Joint Constraint & Satisfaction Rate)**, профилирования задержки (**Latency Profile**), индекса сложности подготовки данных (**DPCI**) и их сквозной связи с показателями экономической эффективности.
* **Выводы по Главе 1.**

### Глава 2. Проектирование и разработка продукта «Harness RAG» (FAISS) и контура дообучения SFT (Ollama)

* **2.1. Формирование корпуса корпоративных данных и формализация реестра ограничений (Constraints)**
  * Разработка базы знаний ИТ-компании (регламенты ИБ, SLA техподдержки, HR-политики, финансовые лимиты) в двух редакциях: базовая (`v1.0`) и обновленная (`v2.0` — изменение 20% нормативов для проверки устойчивости к устареванию данных).
  * Спецификация 5 классов проверяемых ограничений:
    1. Обязательная ссылка на код и пункт корпоративного регламента.
    2. Соблюдение точных числовых и финансовых лимитов.
    3. Выдерживание заданного структурного формата ответа (шаблон / JSON / таблица).
    4. Корректный отказ от ответа при запросе закрытых данных или отсутствии полномочий.
    5. Соблюдение ограничения на максимальную длину ответа.
* **2.2. Разработка программного продукта «Harness RAG» на базе векторной библиотеки FAISS**
  * Архитектура модулей: структурно-семантический чанкинг с метаданными (`chunker.py`), модуль эмбеддингов (`embedder.py`), менеджер индексов FAISS с поддержкой горячего инкрементального обновления документов без полной пересборки (`faiss_store.py`).
  * Реализация модуля **Constraint Harness** (`constraint_harness.py`): динамическое конструирование системного промпта с правилами и алгоритмическая пост-валидация сгенерированного ответа.
* **2.3. Реализация пайплайна подготовки данных и дообучения локальной модели через SFT с развертыванием в Ollama**
  * Конвейер трансформации корпоративных документов в инструктивный датасет `ChatML` (`dataset_builder.py`), очистка, валидация и балансировка примеров.
  * Скрипт дообучения адаптеров `QLoRA` (`train_qlora.py`), слияние весов, квантизация в `GGUF`, сборка модели через `Modelfile` и интеграция с API Ollama (`ollama_manager.py`).
* **2.4. Архитектура автоматизированного испытательного стенда и модуля экономических расчетов**
  * Программная реализация сборщика телеметрии Ollama (`prompt_eval_duration`, `eval_duration`), вычислителя метрики JCR и калькулятора TCO/ROI.
* **Выводы по Главе 2.**

### Глава 3. Экспериментальное исследование по системе метрик и технико-экономическое обоснование (Экономический раздел)

* **3.1. Сравнительный анализ скоростных характеристик (Метрики Latency)**
  * Покомпонентная декомпозиция задержки ответа:
    * Для **Harness RAG**:
      $$L_{\text{RAG}} = T_{\text{embed}}(q) + T_{\text{FAISS}}(q) + T_{\text{TTFT}}(q \oplus D_{\text{top-}k}) + T_{\text{decode}}(y)$$
    * Для **SFT (Ollama)**:
      $$L_{\text{SFT}} = T_{\text{TTFT}}(q) + T_{\text{decode}}(y)$$
  * Сравнение времени поиска в FAISS ($0.5\text{–}4.0\text{ мс}$) с задержкой префилла промпта (**TTFT**) и скоростью генерации (**TPS**). Анализ перцентилей $p_{50}, p_{95}, p_{99}$.
* **3.2. Сравнительный анализ качества и соблюдения ограничений по метрике JCR**
  * Оценка удовлетворенности ответом ($S_i$) и соблюдения ограничений ($C_i$), расчет строгой ($JCR_{\text{strict}}$) и взвешенной ($JCR_{\text{weighted}}$) метрики на базовой редакции документов (`v1.0`).
  * Эксперимент «Устаревание корпоративных данных» (переход на редакцию `v2.0`): количественная оценка падения JCR у SFT-модели из-за инерции весов против сохранения $JCR > 0.90$ у продукта **Harness RAG** после секундного обновления индекса FAISS.
* **3.3. Оценка времени на разработку (Time-to-Market) и сложности подготовки данных**
  * Поэтапный хронометраж разработки и запуска обоих подходов (человеко-часы инженера и эксперта предметной области).
  * Сравнение индекса сложности подготовки данных (**DPCI**) и времени цикла актуализации знаний ($T_{\text{update}}$): доли секунды в FAISS против десятков часов при пересборке датасета и переобучении SFT.
* **3.4. Экономическое обоснование и расчет эффективности внедрения (Экономика проекта)**
  * **3.4.1. Расчет капитальных затрат на разработку и первичное внедрение (CAPEX):**
    * Смета трудозатрат ИТ-специалистов (ML-инженер, аналитик-разметчик), расчет ФОТ со страховыми взносами и накладными расходами.
    * Затраты на вычислительную инфраструктуру на этапе создания (GPU-часы для обучения SFT против CPU-индексации для FAISS).
  * **3.4.2. Расчет операционных затрат на эксплуатацию и актуализацию базы знаний (OPEX):**
    * Стоимость инференса в расчете на $1\,000$ и $100\,000$ запросов (с учетом разницы в длине входного контекста).
    * Годовые затраты на поддержку актуальности знаний при частоте обновления регламентов $M = 1, 4, 12, 52$ раза в год.
    * Оценка стоимости операционных рисков бизнеса от некорректных ответов и нарушений ограничений пропорционально $(1 - JCR)$.
  * **3.4.3. Сравнительный анализ совокупной стоимости владения (TCO), CPUQ, ROI и срока окупаемости:**
    * Расчет **TCO** на горизонте 1–3 лет и построение графика точки безубыточности (Break-Even Analysis).
    * Расчет удельной стоимости единицы качества **CPUQ (Cost Per Unit of JCR Quality)** — затраты в рублях на достижение 1% метрики JCR.
    * Расчет чистого дисконтированного дохода (**NPV**), рентабельности инвестиций (**ROI**) и срока окупаемости проекта (**Payback Period**).
* **3.5. Итоговая матрица принятия технических и управленческих решений**
  * Четкие критерии выбора между легковесным RAG и SFT для корпоративного внедрения.
* **Выводы по Главе 3.**

## 4. Сводная матрица исследуемых метрик

| Группа метрик | Показатель | Формула / Единица измерения | Роль в сравнении RAG vs SFT и экономике |
| :--- | :--- | :--- | :--- |
| **1. Latency (Быстродействие)** | **FAISS Search Time ($T_{\text{FAISS}}$)** | мс ($p_{50}, p_{95}, p_{99}$) | Затраты на поиск в векторном индексе (0 мс для SFT vs 1–4 мс для RAG) |
| | **Time To First Token ($T_{\text{TTFT}}$)** | мс (`prompt_eval_duration`) | Влияние длины подставляемых чанков RAG против короткого промпта SFT |
| | **Generation Speed ($TPS$)** | токенов / сек | Пропускная способность локальной модели в Ollama |
| | **Total Latency ($L_{\text{total}}$)** | мс / сек | Полное время отклика системы для конечного сотрудника |
| **2. Качество и ограничения (JCR)** | **Satisfaction Score ($S_i$)** | $[0..1]$ | Фактологическая точность и полнота ответа по регламенту |
| | **Constraint Compliance ($C_i$)** | $[0..1]$ | Доля выполненных жестких корпоративных ограничений в ответе |
| | **Strict JCR ($JCR_{\text{strict}}$)** | $\frac{1}{N}\sum_{i=1}^{N} \left(S_i \cdot \prod_{k=1}^{K} c_{i,k}\right)$ | Доля полностью эталонных ответов без единого нарушения правил |
| | **Weighted JCR ($JCR_{\text{weighted}}$)** | $\frac{1}{N}\sum_{i=1}^{N} \left(S_i \cdot \sum_{k=1}^{K} w_k c_{i,k}\right)$ | Взвешенный показатель качества с учетом веса каждого ограничения |
| | **Drift Retention ($\Delta JCR$)** | $\%$ сохранения JCR на редакции `v2.0` | Устойчивость системы к обновлению корпоративных данных |
| **3. Разработка и данные** | **Data Prep Time ($T_{\text{prep}}$)** | чел.-часы на 100 документов | Трудоемкость нарезки чанков RAG против разметки датасета SFT |
| | **Data Prep Complexity ($DPCI$)** | баллы $[1..10]$ | Сложность конвейера подготовки, очистки и валидации данных |
| | **Time-to-Market ($T_{\text{dev}}$)** | чел.-часы / дни | Полное время разработки от старта до запуска в эксплуатацию |
| | **Update Latency ($T_{\text{upd}}$)** | секунды (RAG) vs часы (SFT) | Оперативность реакции системы на изменение внутренних правил |
| **4. Экономика (TCO / ROI)** | **Капитальные затраты ($CAPEX$)** | тыс. руб. | Первичная стоимость разработки, подготовки данных и обучения |
| | **Операционные затраты ($OPEX$)** | тыс. руб. / год | Затраты на инференс + регулярные циклы обновления базы знаний |
| | **Совокупная стоимость ($TCO$)** | $CAPEX + \sum_{t=1}^{T} OPEX_t$ (тыс. руб.) | Полный бюджет владения системой на горизонте 1–3 лет |
| | **Стоимость 1% качества ($CPUQ$)** | $\frac{TCO_1}{JCR_{\text{strict}} \cdot 100}$ (тыс. руб. / % JCR) | Экономическая эффективность вложений в качество ответов |
| | **ROI, NPV, Срок окупаемости** | $\%$, тыс. руб., месяцы | Итоговая инвестиционная привлекательность внедрения на практике |
